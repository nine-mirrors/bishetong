## 四、改造方案

### 4.1 作品定位

- **暂定名称**：毕设通 —— 毕业设计全流程管理系统
- **一句话**：连接学生、导师、教务，用任务化协作替代「微信群 + Excel + 邮件」的碎片化管理，并用 AI 识别进度风险。
- **目标用户与痛点**

| 角色 | 现状痛点 | 系统解决 |
| --- | --- | --- |
| 学生 | 不知道每个节点该交什么；材料版本混乱；催办靠群消息 | 阶段看板 + 里程碑待办 + 文档版本 + 自动提醒 |
| 导师 | 同时带多个学生，进度靠问；批阅意见散落 | 学生进度总览 + 在线批阅 + 风险名单 |
| 教务 | 中期检查靠收表；逾期数据事后才知道 | 全局看板 + 逾期统计 + 一键导出 |

- **三个「非 CRUD」卖点（答辩主要讲这三个）**

| 卖点 | 技术实现 | 可讲的内容 |
| --- | --- | --- |
| 三方协同状态机 | 阶段枚举 + 状态迁移校验 + 角色权限矩阵驱动 | 为什么不能让状态随意跳、如何防止越权操作 |
| 进度风险预警 | 多因子加权评分（逾期天数、里程碑完成率、提交间隔、批阅响应时长），输出可解释的风险因子 | 指标怎么定、权重怎么调、如何避免误报 |
| AI 能力（只选 1 项） | 见 4.7 | 输入输出边界、人工可覆盖、幻觉如何规避 |

- **明确不做**（防止范围失控）：不做通用项目管理（会与 A 方向同质化）、不做即时通讯（站内通知足够）、不做移动端 App、不做三个 AI 功能。

### 4.2 技术架构

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | 现有 Vue 3 + Vite + Pinia + Element Plus | 直接复用 |
| 后端 | Node.js + Express（或 NestJS） | 与前端同语言，答辩好讲 |
| 数据库 | MySQL + Prisma ORM | Schema 可直接放进设计文档当 ER 图 |
| 鉴权 | JWT + RBAC（student / advisor / admin） | 多角色是常见加分点 |
| 文件 | 本地静态目录 + 上传大小/类型校验 | 演示够用，避免额外依赖 |
| 通知 | 站内通知表 + 轮询（或 SSE） | 不引入 WebSocket 复杂度 |
| 测试 | Vitest（单元）+ Playwright（E2E） | 与 Vite 生态一致 |
| 部署 | 后端 Docker + 云服务器；前端 Vercel/Netlify | 必须有公网地址 |
| CI | lint + build + test 三步 | 在现有 ci.yml 上扩展 |

### 4.4 数据模型

```
users(id, name, email, password_hash, role[student|advisor|admin],
      student_no, department, created_at)

topics(id, title, description, advisor_id, capacity, status, created_at)

topic_applications(id, topic_id, student_id, statement, status[pending|approved|rejected],
                   reviewed_by, review_comment, created_at)

projects(id, topic_id, student_id, advisor_id, title,
         current_phase[topic|proposal|midterm|defense|archived],
         start_date, defense_date, status)

milestones(id, project_id, name, phase, due_date,
           status[pending|submitted|approved|rejected|overdue],
           submitted_at, reviewed_by, review_comment)

documents(id, project_id, milestone_id, file_name, file_path,
          version, uploaded_by, uploaded_at)

notifications(id, user_id, type, title, content, is_read, created_at)

activity_logs(id, user_id, action, target_type, target_id, created_at)
```

> 风险分不建表，按需实时计算并缓存；若要做趋势图，再存 `risk_snapshots(project_id, score, factors_json, created_at)`。

### 4.7 功能分层（严格按此收敛）

#### 必做（MVP，缺一项就不能演示完整闭环）

1. 登录注册 + 三角色权限
2. 课题发布 → 学生申请 → 导师审批
3. 项目立项 + 阶段状态机（选题 → 开题 → 中期 → 答辩 → 归档）
4. 里程碑：创建、到期提醒、提交、批阅
5. 文档上传与版本管理
6. 站内通知（提交、批阅、逾期）
7. 列表分页/搜索/详情、空状态/错误态/Loading 全覆盖

#### 加分（时间允许再做，选 2 个）

- 教务数据看板（进度分布、逾期率、导师负载）
- 操作日志 / 审计
- Excel / PDF 导出
- 邮件通知

#### 差异化（只做 1 个，做透）

| 选项 | 实现方式 | 难度 | 建议 |
| --- | --- | --- | --- |
| **进度风险预警（推荐）** | 规则 + 加权评分：逾期天数、里程碑完成率、提交间隔、批阅响应时长；输出前 3 个风险因子与建议动作 | 中 | 数据自产、可解释、不依赖外部 API，答辩最稳 |
| AI 选题匹配 | 学生填研究方向与关键词，与导师课题做相似度匹配并给出理由；需处理冷启动 | 中高 | 需要足够课题数据 |
| AI 开题报告合规检查 | 对照模板检查结构完整性、必填项、字数、引用格式，给出修改建议 | 中 | 容易做成"套壳"，必须强调规则 + 模型混合 |

> **硬性约束：三个 AI 选项只能选一个。** 做三个必然每个都做不深，反而扣分。

### 4.10 里程碑与验收标准

| 阶段 | 目标 | 验收标准（全部可勾选才算完成） |
| --- | --- | --- |
| **M0 调研定题** | 确认真实痛点 | 完成 3—5 份访谈（学生 2—3、导师 1、教务 1）；输出痛点清单；确定风险评分指标 |
| **M1 骨架打通** | 真后端可用 | 登录 + 三角色 + 课题 + 申请流程跑通；前端已替换 Mock；`docs/api.md` 与实际接口一致 |
| **M2 主流程** | 业务闭环 | 申请 → 立项 → 里程碑提交 → 导师批阅 全链路可演示；三种角色视图正确 |
| **M3 亮点** | 差异化落地 | 风险评分上线且可解释；看板至少 3 个图表；有真实或模拟数据的对比说明 |
| **M4 质量与部署** | 可交付 | 测试通过、CI 全绿、公网可访问、一键启动脚本可用 |
| **M5 答辩准备** | 能讲清楚 | 5 份文档 + 视频 + PPT 完成；至少 3 次计时彩排；每个亮点都有「为什么 / 坑 / 解法 / 效果」四段式 |

### 4.11 主要风险

| 风险 | 应对 |
| --- | --- |
| **范围失控（最大风险）** | 严格按 4.7 分层，MVP 未完成前不碰加分项；AI 只做 1 个 |
| 后端不熟卡进度 | Express + Prisma，只写最简单的 REST，不做微服务 |
| 拿不到真实用户 | 先访谈同班同学与自己的导师，样本量 3—5 即可 |
| 导师/教务配合度低 | 系统先按"学生 + 导师"两角色做通，教务角色做只读看板 |
| 答辩讲不出技术点 | 每个亮点准备数据支撑（如风险预警的命中率对比） |
| 规则变化 | M5 前对照官网当年模板逐项核对 |
